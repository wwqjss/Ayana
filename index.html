AYANA · PRODUCT BRIEF

把监控收拢成一条
能说清楚的链路

你们和 GPT 梳理的八个问题，根子不在「界面不好看」，而在监控对象、健康状态、告警规则、事件处理没有被同一套语言串起来。 下面是我基于代码现状（web.py 导航、health.py、monitor.py、promconfig.py）给出的提议： 先收口信息架构，再统一健康语义，最后补上「轻量原生探测」这条你们最初想要却没落地的腿。

对象 Ayana v0.2.0 → v0.6.x 范围 产品结构 / 监控健康 / 规则体验 原则 不造时序库 · 不重复入口 · 不把缺测装成正常

先把问题定性，别混在一起修

同一张截图上的「红点」和「总览告警」，可能来自三类完全不同的债。混着修会修成第二套混乱。

类型 对应你们讨论 性质 处理方式
已确认缺陷 图表不可读 · 指标过度拆分 · 无数据占位 · 总览过载 · 小圆点说谎 · 消息/通知拆散 · 高级 Prom 重复入口 现状明确，用户已经踩到 直接进 P0/P1，按「收口」而不是「加功能」修
未完成能力 Ayana 原生轻量探测（Ping / TCP / HTTP / 服务 / 容器） 产品目标偏移：Prom 管理越做越厚，原生探测缺席 单独立项补腿，不要再往 promconfig 上堆
讨论中的设计 可视化告警规则（开关 + 阈值 + 时长 + 按主机覆盖） 需求方向合理，但细节尚未拍板 先定语义和数据模型，再画 UI；不要先做漂亮表单

我的总态度：你们讨论的判断基本成立。需要收窄的只有一句—— 「整个高级 Prom 都要处理掉」应理解为取消独立顶级入口， 而不是删除规则校验、回滚、原文编辑这些能力。能力要下沉，不能一起扔掉。

01

信息架构：三页定生死

现在导航是：总览 / 事件 / 检查 / 资源 / 高级·Prom / 消息记录 / 连接 / 通知 / 知识 / 权限 / 审计—— 11 个顶级入口里，至少 4 个在互相讲同一件事。

现状导航 · 同一事实散落四处
总览 事件 检查 资源 高级·Prom 消息记录 连接 通知 知识 权限 审计

高亮的四个入口，都承载「监控是否正常」——这是重复与不一致的来源。

目标：按「人要做什么」分页，而不是按「后端有什么模块」分页

PAGE 01

总览 = 待办驾驶舱

只放需要人关注、处理、审批的事项：需人工事件、待批准操作、采集中断。正常运行的几十个对象不进首页。

PAGE 02

事件 = 完整生命周期

告警归并、调查、处置、验证、结案。筛选与时间线在这里，不在总览里复述。

PAGE 03

资源 = 监控唯一真相

主机健康、指标图表、探测项、接入状态、告警规则、Prom 配置能力全部收进这里。小圆点只在这里被解释。

BEFORE · 重复与分散
  • 总览展示完整监控状态列表
  • 资源再展示一遍主机与指标
  • 高级·Prom 里还能「主机接入监控」
  • 通知 / 消息记录 两个顶级入口
AFTER · 一处定义，一处操作
  • 总览：只显示「需要你动」的
  • 资源：监控对象 / 接入 / 规则 / 配置
  • 接入入口全站唯一（在资源）
  • 通知：渠道 + 消息记录（内标签）
图 1 · 信息架构收拢：删的是入口，不是能力。「高级·Prom」以「规则 / 配置 / 接入」标签活在资源页里。

资源页内部建议二级结构： 「主机与指标」→「监控对象」→「告警规则」→「Prometheus 配置（含校验 / 回滚 / 原文）」→「接入与探测」。 用户在资源页可以完成从「看到红点」到「改一条阈值」的完整闭环，不必跳走。

02

健康语义：小圆点必须说真话

这是你们讨论里最关键的一条。现在资源页主机按钮的绿点，只代表「主机能连」， 而总览里 NERV / Sora / ROMI 已经在告警——同一个对象，两套真相。

代码里其实已经有半套语义（health.py 的 healthy / degraded / unhealthy / unknown / stale， 以及 monitor.py 的 ok / warn / bad / no_data / collect_error）。 问题不是没写状态，而是小圆点没有绑定到「关联监控对象的聚合健康」。

统一状态机（对外只保留 5 态）

显示 状态 判定含义 不包含
绿 · 正常 该主机相关监控均新鲜且成功 不能仅凭「无 Incident」
黄 · 警告 存在 warn 级探测/阈值，或部分降级 不是「将就正常」
红 · 严重 存在 bad / critical 监控失败 历史未结案事件不自动染红
灰 · 无数据 查询成功但无样本 / 未接入 数值为 0 ≠ 无数据
紫 · 采集故障 查询失败、超时、源不可用，无法可靠判断 绝不能伪装成绿或灰
图 2 · 小圆点 = 主机下所有监控对象的聚合健康，不是 SSH 可达性。采集故障优先于「无数据」。

三条硬规则

  1. 聚合优先级： 采集故障 > 红 > 黄 > 灰 > 绿。 任一对象采集失败，整机显示紫——因为此时不能假装知道健康。
  2. 历史事件不粘色： 未结案 Incident 影响「待办」，不直接决定小圆点。 监控恢复后点变绿，事件仍可在事件页保持 open，直到人工确认——这两件事解耦。
  3. 0 ≠ 无数据： value=0 是有效样本（例如磁盘使用率 0%、成功率 0% 也要显示）。 只有「查询成功但序列缺失」才进灰，「查询失败」才进紫。

实现提醒：请把 health.py 的对象健康与 monitor.py 的指标状态合并成一个 host_health(asset_id) 纯函数，Web / QQ / 总览 / 资源全部只消费它的结论。 现在 computeAssetHealth 在 app.js 前端还有一份推断，这正是「两套真相」的技术根因。

03

指标展示：合并、排序、能判断故障

现在的 drawSpark 只画一条无坐标轴、无悬停、无对比的装饰曲线。 运维要的不是「看起来有监控」，而是「出了问题能不能从图上看出什么时候坏的」。

指标合并（你们的判断我完全同意）

现状 改为 理由
load1 / load5 / load15 三张卡 一张 Load 图，三条线 + 图例 短长期负载要在同一时间轴上对比，拆开就失去意义
net_rx / net_tx 两张卡 网络一卡，收/发双线（对称轴更好） 判断「断流」要看方向，不能分页看
disk_read / disk_write 磁盘 IO一卡，读/写双线 同上
cpu / memory / swap / disk 可保留 单序列大图，带阈值参考线 与告警阈值对齐，图上就能看出「为什么触发」

排序：无数据沉底，但绝不伪装

展示顺序

1 有数据且异常 → 2 有数据且正常 → 3 无数据 / 未启用

「正常且有数据」的优先展示；「无数据、未启用、采集失败」沉底或折叠。沉底不等于隐藏，页脚要有汇总一行。

图表最低标准

时间轴 · 数值刻度 · 悬停详情 · 阈值线

悬停显示 时刻 / 值 / 系列名。时间范围切换（1h / 6h / 24h / 7d）要保留在图区上方，而不是整页刷新。

图 3 · 从 11 个碎片到 4–6 张有坐标轴的图；Load / 网络 / 磁盘 IO 必须同图多序列。
04

双轨监控：轻量原生 + Prometheus

这是产品目标偏移最严重的一块。Prometheus 管理（promconfig 已经 100KB+）越做越厚， 而「不依赖 Prometheus 的简单探测」并没有形成完整体验。

图 4 · 简单监控 Ayana 自己做，复杂监控交给 Prometheus，告警都进同一条事件管道。

原生轻量探测的边界（要克制）

  • 做：连通性、端口、HTTP 状态码/关键字、systemd/Windows 服务、Docker 容器状态。周期可配（默认 60s）。
  • 不做：长期时序存储、复杂 PromQL、录制规则、多租户指标网关。README 里「不在 Ayana 落时序」应继续成立。
  • 产出：每个探测项的最近状态 + 失败原因 + 最近 24h 成功/失败计数（够画 spark、够判健康即可）。
  • 告警：探测失败可直接产生 Event（不经过 Alertmanager），与 Prom 告警在 alert_episodes 同表归并。

接入入口全站唯一： 资源页「接入」标签提供两条路径——「一键接入 Node Exporter」（已有，保留）与「添加轻量探测」（新建）。 高级·Prom 里的任何接入按钮删除；Prometheus 配置里的 target 只读展示 + 从 Ayana 托管的 file_sd 增删。

05

规则管理：从 YAML 到「开关 + 阈值」

日常告警不该会写 PromQL。但底层原文能力不能删——给高级用户和故障逃生用。 所以是两层 UI，不是两套功能。

日常层 · 所有人

可视化规则卡片

「CPU 使用率超过 85%，持续 5 分钟，严重」—— 开关、阈值、时长、级别，四个字段搞定 80% 规则。 默认规则作用于所有主机；特殊主机可覆盖阈值。

高级层 · 运维/逃生

原文编辑与变更

YAML/PromQL 原文、promtool 校验、diff、应用、回滚—— 从「高级·Prom」下沉到资源 → 规则 → 「高级」标签。 规则来源徽章：Ayana 托管 外部 Prometheus

规则对象模型（先定语义）

字段 说明
scope global（所有主机）或 host（指定资产覆盖）
metric_key 语义键：cpu / mem / disk / load / probe…，由模板编译成 PromQL 或原生探测条件
comparator / threshold / for > >= < ，数值，持续时间——UI 上就是三个控件
severity info / warn / critical → 对应小圆点黄/红
source ayana_managed 可在 UI 编辑；external_prom 只读标注，避免双写
compiled 缓存编译后的 PromQL/YAML 片段；原文层可查看生成结果

不要做的：不要把外部 Prometheus 规则「导入再同步回去」。 外部规则只读展示 + 状态，避免双主写入导致配置漂移——这也是删除重复「主机接入」入口的同一逻辑。

06

底层对象模型：一条链说清

界面收拢之前，对象关系必须先统一。否则改完导航，数据还是散的。

图 5 · 健康由探测与规则推出；告警进入事件；事件驱动调查与处置。小圆点只读 Health，不读 Incident 历史。

关键不变量

  • host_health 只依赖：新鲜的探测/指标样本 + 规则评估结果 + 采集链路状态。
  • Incident 的 open/closed 影响总览待办，不反向染色小圆点。
  • 一个 MonitorObject 只有一个接入定义；UI 上不允许两处都能「一键安装 / 停止」。
  • 通知渠道与消息记录共享同一 outbox 事实源，只是入口合并。
07

落地路线：先收口，再补腿

不要一上来做大重构。按「用户下一眼就能感到不一样」的顺序切。

阶段 1
P0 · 1 周

信息架构收口 已确认缺陷

导航改为：总览（仅待办）/ 事件 / 资源 / 通知（渠道+消息记录）/ 其余收进设置或保持。 删除「高级·Prom」顶级页，能力迁入资源。删除重复接入入口。 验收：全站只有一处能装/卸 Node Exporter。

阶段 2
P0 · 1 周

健康语义统一 已确认缺陷

合并 health.py / monitor.py / 前端推断 → 单一 host_health。 小圆点接上聚合健康；采集故障独立色；历史事件不粘色。 验收：总览有告警的主机，资源页小圆点必定不是绿。

阶段 3
P1 · 1–2 周

指标图表可读 已确认缺陷

Load/网络/磁盘 IO 合并；时间轴+悬停+阈值线；无数据沉底。 验收：不看文字也能说出「几点开始变差」。

阶段 4
P1 · 2 周

原生轻量探测 未完成能力

Ping / TCP / HTTP / 服务 / 容器；配置在资源页；失败直接进事件管道。 验收：拔掉 Prometheus，Ayana 仍能发现「网站挂了」。

阶段 5
P2 · 2 周

可视化规则 讨论中的设计

开关+阈值+时长+按主机覆盖；高级层保留原文/校验/回滚。 验收：不懂 PromQL 的人能改完「CPU 85% / 5 分钟」并生效。

08

验收标准（可拿去对截图）

  • 首页没有任何「正常运行」的完整监控列表；有也只是折叠摘要。
  • 资源页主机小圆点颜色 = 该主机监控聚合健康；与总览告警一致。
  • Load / 网络 / 磁盘 IO 各只有一张多序列图；图有时间轴与悬停。
  • 无数据指标沉底；采集失败显示独立状态，绝不显示「正常」。
  • 「通知」内能切换「渠道 / 消息记录」；不存在两个顶级入口。
  • 全站唯一「主机接入监控」入口。
  • 无 Prometheus 时，至少 Ping/TCP/HTTP 探测可用并进事件。
  • 一条规则可在 UI 用「阈值 + 时长」表达，并能看到编译后的原文。
09

与 GPT 讨论的差异点

讨论中的表述 我的修正 原因
「整个高级 Prom 都要处理掉」 删顶级入口，保留能力（校验/回滚/原文/diff） 能力有价值，错的是位置与重复入口，不是功能本身
「消息记录和通知放一起」 同意；并要求消息记录可按 Incident / 渠道筛选 合并入口之后，消息日志仍要能回答「这条告警发到哪了」
「历史事件未结案不该导致红色」 完全同意，并升格为不变量：Incident 不反向决定 Health 恢复与结案是两个时间尺度，混在一起会制造假红
可视化告警规则（细节未定） 先定 scope/severity/source/compiled 字段，再画 UI 避免做成「另一套阈值配置」与 Prom 双写
原生轻量监控「尚不能确认是否实现」 按代码看：monitor.py 是 Prom 查询侧，原生探测引擎应视为未完成 monitor.py 依赖 Prometheus/Node Exporter；checks.py 偏连接检查，不是通用探测引擎

一句话总结： 第一层界面问题，按「三页定生死 + 合并入口」一周可感觉到变化； 第二层产品逻辑问题，要把「资产 → 监控对象 → 探测 → 健康 → 告警 → 事件」写成同一套不变量， 否则界面改完还会裂开。你们已经抓对了根因，接下来缺的是把「双轨监控」和「健康聚合」当成正式功能立项，而不是继续在 Prom 管理上加厚。
