# 自然语言智能填表

> 历史说明：独立智能填表层已于 2026-10-29 清理，`/api/assist/configure` 返回退役提示。当前通过 [MiMoCode MCP 操作接口](mcp-operations.md) 配置监控，或使用 Web 手工表单。以下内容仅用于查阅旧实现。

智能填表把自然语言转换成可修改、可校验的表单草稿。它不保存配置、不执行探测命令，也不替用户确认。主机、检查对象和权限操作来自服务器当前可见的配置，模型不能创建不存在的资产或扩大执行权限。

## 实现入口

| 文件 | 职责 |
| --- | --- |
| `ayana/formspec.py` | 表单字段、显示标签、默认值、约束、条件和提交适配器的共同来源 |
| `ayana/assist.py` | 根据真实表单和服务器上下文调用模型，校验结构与字段，准备草稿、追问及确认事项 |
| `ayana/llm.py` | 模型 HTTP 适配器，保留超时、HTTP 错误、响应格式错误和截断状态 |
| `ayana/web.py` | 鉴权、可见资产与能力上下文、智能填表接口，以及提交前校验接口 |
| `ayana/checks.py` | 创建、更新与实际执行业务检查；创建和更新复用表单校验 |
| `ayana/static/app.js` | 按表单定义填入控件，保留人工修改，展示追问、校验结果及最终确认 |

模型上下文包含启用且当前账号可见的资产、显示名称和已登记对象。客户端不能通过 `context.assets` 或 `context.capabilities` 增加选项。已登记对象表示配置事实，不表示已经确认目标服务当前正在运行。智能填表阶段不会连接目标机执行验证。

## 共用表单契约

`get_form(domain)` 返回当前表单。每个字段声明 `name`、`type` 和 `label`，并按需要声明枚举、长度、数值范围、格式、默认值、选项来源及条件。前端控件使用 `control` / `control_id`，展示枚举使用 `value_labels`。`applicable_if` 与 `required_when` 使用受限条件对象；当前支持 `field` 配合 `equals` 或 `in`，以及 `all` 组合，不执行表达式字符串。

`form_prompt_payload()` 从同一份定义构造模型提示词。`validate_fields()` 接受声明过的平铺或嵌套字段，返回：

```python
{
    "fields": {...},
    "issues": [{"field": "...", "label": "...", "message": "...", "code": "..."}],
    "missing": [{"field": "...", "label": "...", "question": "..."}],
    "defaulted": ["..."],
    "payload": {...} or None,
    "valid": True or False,
}
```

缺失项与错误项分别报告。未知字段、重复值、无效类型、越界数值、非法资产和无关字段不会被悄悄丢弃后当作成功。整数不接受布尔值或小数；数值不会自动限制到范围边界；模型给出的过长名称不会被截断。用户可使用中文自然语言名称，检查的内部唯一标识由系统生成。

业务检查界面的字段与提交字段通过服务器适配器转换：

| 表单字段 | 实际提交字段 |
| --- | --- |
| `params.proto` | `params.protocol` |
| `params.cmd` | 校验后的 `params.argv` |
| `expect.mode=exit0` | `expect.exit_code=0` |
| `expect.mode=contains` 与 `expect.value` | `expect.output_contains` |
| `expect.mode=not_contains` 与 `expect.value` | `expect.output_not_contains` |

`check_payload()` 校验表单字段并生成提交内容。`payload_to_fields()` 和 `validate_check_payload()` 校验已有的提交结构，拒绝不能表达为当前表单的额外参数或期望组合。检查服务的创建、更新也调用共同校验入口，前端通过了预览并不意味着后台可以跳过约束。

## 理解、追问、确认和提交

1. `POST /api/assist/configure` 接收自然语言及受限的续答上下文，向模型提供真实表单和服务器选项。
2. 模型必须返回结构化草稿。系统校验路由、元数据、字段和实际提交约束；无效结果最多修正一次。
3. `needs_input` 只询问尚缺少的必要信息或尚未确定的选择。选项可包含区别说明。`needs_confirmation` 保留需要用户核对的推断。`unsupported` 说明能力限制，不自动换成另一个监控目标。
4. 续答携带原始需求、当前草稿与用户答案。检查表单使用当前控件内容，人工修改会进入下一轮上下文。迟到的模型响应不能覆盖用户在请求期间所作的修改。
5. 用户可继续修改任何字段。业务检查创建前调用 `POST /api/checks/validate`；权限保存前调用 `POST /api/permissions/validate`。两者都展示服务器返回的实际配置摘要，再明确确认。
6. 确认后提交校验返回的配置。取消确认不写入。表单修改后必须重新校验。保存接口仍检查账号、CSRF、管理权限和授权策略。

概念澄清与字段补充使用不同协议。用户用用途、背景、简称等描述一个尚未确定的对象时，模型返回 `clarifications`，而不是新增不存在的表单字段，也不把背景直接当作检查目标。每项包含独立的 `id`、显示标签 `label`、问题 `question` 和可选的 `options`。例如两个组件都可能负责后台任务，先解释区别并确认要观察哪一个；候选只是待确认的理解，不表示服务器已登记或实际观察到该组件。

澄清选项的 `value` 是非空、长度受限的自然语言回答。接口把问题映射为 `clarification.<id>`，统一放入 `missing` 展示，选项标记 `mode=answer`。选择选项或填写“还不清楚”只进入下一轮 `context.answers`，不会赋给服务名称、对象标识或其他字段。模型收到原始需求、当前草稿和答案后，返回完整更新后的草稿，仍需通过实际表单校验。

针对真实字段的 `missing.options` 默认使用 `mode=field_value`，每个选项必须满足该字段及当前资产、能力、对象类型的约束。描述性的回答可显式使用 `mode=answer`，作为对话补充。系统拒绝空值、未知选项模式和不适用于当前配置的字段问题；概念问题不得以此绕过字段约束。

尚有概念问题时，界面只展示澄清问题，延后追问底层服务标识、命令等字段，也延后单独的推断确认。已确定的字段继续填写并校验。所有需要补充或确认的草稿都返回 `ready_to_submit=false` 和 `payload=None`；只有准备完整且无需进一步澄清的配置才提供待预校验的提交内容。最终创建或保存仍须经过用户确认。

推断确认针对上一轮明确展示的问题与配置值。确认答复与上一轮问题完全对应、且本轮被推断字段没有改变时，不因模型再次附带相同推断说明而重复确认。模型改成了其他对象，或答复没有对应原问题时，仍需核对新的理解。这一步仅确认理解，不能替代最终创建或保存的确认。

权限助手区分默认授权与单台资产例外，路由与范围不能矛盾，不能把指定主机或对象的授权变成全局默认。指定对象使用所属资产的登记标识；明确且唯一的服务名、容器名或对象名称可转换成该标识，存在歧义时列出实际对象供用户选择，不退回全部对象。操作必须支持相应对象类型。

策略还受真实能力目录约束：只读操作使用禁止或允许读取，不能把“需要审批”保存成一个实际不会审批的读取策略；写操作的自动执行须符合源码能力边界。权限校验生成与实际保存接口对应的布尔授权配置，保存时再次核对 Agent 策略的范围、对象与状态，人工修改不能绕过校验。查看生效权限和打开权限上限页面属于查询、定位，不要求用户填写新策略，也不会自动保存权限。

普通界面显示识别结果、默认值、必要问题和配置摘要。模型说明中的已知字段、能力与资产引用按真实显示标签呈现；已知服务状态命令以服务运行状态说明呈现。这一处理只改变说明文字，不改变模型意图或表单值。原始模型结构、内部字段和诊断保留在高级区域。

## 失败与真实能力边界

模型未配置、连接失败、超时、输出结构异常、截断或重复校验失败时，界面明确报告失败，保留人工填写路径。系统不会转回关键词匹配后声称理解成功。完整 JSON 可兼容代码块和字符串外的尾逗号；截断内容不能通过补引号或补括号变成草稿。部分模型把空的可选 `unsupported` 返回为空对象，此类无语义的格式差异会记录在诊断中；实际不支持说明仍须提供有效原因。

当前业务检查的 `service` 类型仅通过 `systemctl is-active` 判断 **systemd 服务**是否运行。它不能直接检查 Docker 容器或 Kubernetes Pod。能力目录的其他操作可能支持容器，这不表示业务检查表单自动拥有相同能力。

`port` 类型检查目标端口监听；`command` 类型只接受现有只读程序、参数和受限执行通道。网页检查不能通过写入请求或下载文件改变目标机。命令格式有效也不能扩大主机上的命令白名单或授权边界。

提交失败提供具体、可读的原因及字段问题。内部错误码保留给接口与调试使用，普通界面优先显示 `message` 和字段的 `message`。

## 扩展到新表单

1. 在 `formspec.py` 注册真实表单及场景映射，声明字段、条件、默认值、显示标签、控件映射和实际能力边界。不要加入某台主机、某个服务或某句话的标准答案规则。
2. 为新表单增加明确的提交适配器与逆向校验，接入共同校验入口；最终保存服务也必须使用同一校验。复杂结构不能只靠客户端拼接。
3. 在智能填表路由中注册支持的操作，并由服务器提供当前账号可用的资产、对象和选项。客户端续答只能携带用户输入与草稿，不能成为权限或资产来源。
4. 前端按字段定义填表、显示问题与摘要；新增保存操作须沿用校验、人工确认和提交顺序。原始模型输出继续放入高级区域。
5. 补充与示例无关的回归：不同资产和对象、缺失信息、歧义选项、续答纠正、非法输出、人工修改，以及取消确认不写入。

目前注册表单为业务检查与权限配置。新表单需要接入适配器、路由和保存服务，不能仅添加一份字段列表便认为已经实现完整链路。

## 验证

在仓库根目录运行，使用项目 Python 依赖和可用的 Node.js：

```text
python -m unittest discover -s tests -p "test_assist*.py"
python -m unittest discover -s tests -p "test_formspec.py"
python -m unittest discover -s tests -p "test_checks.py"
python -m unittest discover -s tests -p "test_llm.py"
node --check ayana/static/app.js
node tests/test_assist_ui.cjs
python -m unittest discover -s tests
```

智能填表测试使用受控模型响应，验证草稿、续答、歧义、失败、展示和提交链路，而不是检查是否出现固定示例答案。它还检查概念澄清、未知回答与直接填写值的隔离，异常问题协议、非适用字段和澄清期间的校验边界。API 测试使用临时数据库，确认草稿与预校验不创建检查、不修改权限、不执行探测。模型适配器测试使用本地 HTTP 服务，覆盖实际请求格式、超时、错误分类和截断状态，不需要外部密钥。

Node 测试使用 DOM 模拟，覆盖字段适用条件、旧字段清理、请求竞态、人工修改、校验与取消/确认行为。它不能代替浏览器视觉验收。真实模型验收还应核对不同表述与实际服务器上下文，确认无写入后再测试明确确认的提交；不要在日志中输出模型密钥、连接凭据或完整配置文件。
