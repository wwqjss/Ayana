## 原驱动复核与不能冒称的结果

原 `tmp-p43-e2e.py` 已由上一位工程师删除。本次从历史 write 和 9 次 edit 记录在内存恢复审阅，记录了来源 part ID、内容哈希及删除记录，没有把含本机路径和宽松判据的临时驱动重新加入仓库。

发现原驱动 `incident_not_auto_closed` 使用 `or True`、`readonly_rejects_write` 为常量，真实调用判据也接受模型自报。因此本次通过结论来自原始 tool parts、模型日志和数据库的独立核对，不采信这些弱判据。

以下范围必须明确：

- 真实的是 MiMo 模型调用、MCP 进程及工具执行、Worker 结果回写；告警本身为模拟。
- 此运行直接调用 ingest 方法，未验证 live HTTP/Alertmanager 网络入口。
- 非 JSON、API 失败、超时/冷却等故障注入使用 BadMimo/FailMimo；本轮单元回归也使用 mock。它们只作为负面/降级测试，不计作真实模型 E2E。
- Prometheus 连接被拒并熔断；SSH read endpoint 不存在；因此未获得真实主机诊断结果，根因保持 `unknown`。
- driver 的知识根为隔离 `kb`，MCP 使用默认知识根，两者不一致。真实 knowledge 工具成功执行但返回空结果/条目不存在，不能声称真实知识命中。
- 历史运行 native 工具调用为 0，但配置没有硬禁 shell/write/edit。历史证据只证明当次实际调用行为；本轮新增权限门禁须与历史运行区别说明。

## 修复与审查

1. 保留 MiMo 已做的 SessionBridge 修复：首轮/续接返回完整 text，取消 500/2000 字截断；摘要仍在展示/错误字段按需截取。
2. 结论解析支持嵌套、围栏、转义和末尾 JSON；无合法 status 或字段类型错误时降级，工具返回 JSON 不再冒充调查完成；无 evidence 时 root_cause 强制 unknown。
3. 取消序列化 JSON 后的 8000 字硬截断，长结论保持可解析并完整落库；首轮和续接均覆盖。
4. MCP launcher 从脚本位置计算仓库根，移除本机绝对路径；MiMo 有 cwd 时显式传 `--dir`，避免读错项目 MCP 配置；Windows stdio 强制 UTF-8。
5. readonly host.exec 复用既有严格命令参数白名单并安全引用，拒绝复合 shell、重定向、写参数/未知命令；继续走 read 通道、既有主机密钥验证和 SSH 权限边界。拒绝并审计 incident.note/session.remote，原有 upsert/close 拒绝仍保留。
6. 新 generation 重置轮次及旧结论/错误；任务领取、结束回写绑定 generation，旧代结果不能覆盖新任务或写知识。
7. 自动知识固定 speculation，使用独立文档 ID，并拒绝覆盖已升级为事实的文档；同名 verified 文档不受影响。
8. readonly MiMo client 显式选择专用 `ayana-readonly` agent，以精确 7 工具 allowlist 和默认 deny 限制原生工具/写 MCP；保留 provider、MCP 及其他 agent 配置，无效配置在子进程启动前拒绝。允许的 `mcp_tool_search` 只搜索经过 allowlist/权限过滤的目录，不能加载额外写工具。

本机 MiMo CLI `0.1.12` 的真实离线验证确认专用配置被解析、隔离 MCP 可连接、stdio 可发现这 7 个工具、`debug agent --tool bash` 被拒；工具搜索目录的过滤顺序另经本机 CLI 内嵌实现静态检查。两类证据明确区分，未把静态检查冒称为真实模型调用。详见 [P4.3-READONLY-CLI-VERIFICATION.json](P4.3-READONLY-CLI-VERIFICATION.json)。该配置是 CLI 工具层边界，不宣称为操作系统进程沙箱。
