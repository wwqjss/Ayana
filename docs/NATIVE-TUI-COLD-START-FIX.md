# 原生工作台普通新建黑屏与接管无响应修复

日期：2026-10-27（Asia/Shanghai）。分支 `speed-supreme`，基线 `6903fcc`。

## 问题与原验收缺口

用户发现：已有验收会话可见，普通新建长时间黑屏，接管输入后页面没有及时反馈。此前测试检查了后台 tmux 内容和固定尺寸的 PTY，但没有用真实终端解析器执行普通新建和连续输入；因此不能据此认定浏览器操作路径完整可用。

实机检查表明，新建会话后台最终已有欢迎页，接管查询也曾到达 MiMo 并得到回答，问题集中在启动阻塞和终端显示/输入就绪判断。

## 根因与修复

1. 原生 `/provider` 约 6.9 MB、99,014 个字符串。旧递归脱敏对每个字符串重新读取并解析提供方配置，阻塞 runtime 事件循环。200 次读取样本耗时 0.059 秒，按目录规模估算约 29 秒；用户 pane 日志显示初始化延迟 29～53 秒。
2. 每个响应现在只取一次密钥快照，递归处理不再进行文件 I/O；下一响应重新获取快照以支持轮换。真实完整目录处理实测 1.081 秒，仅读取一次配置，保留 Bearer 遮蔽与配置异常失败关闭。
3. 支持严格限定的 DECRPM 终端能力回复，启用 xterm 窗口/单元格/字符尺寸只读报告。普通文字、Return、编码键盘事件、OSC52 剪贴板控制仍不能通过观察模式发送。
4. 只有 xterm 解析完成且可见缓冲区出现文字后才标记画面就绪。初始清屏、探测字节不再算作已显示；画面出现前不开放接管。
5. 合并重复尺寸通知，防止 fit、onResize 和观察器重复触发相同窗口调整。
6. 原生 pane 启动前先持久化 RID 范围绑定，关闭快速初始化时的鉴权竞态。补充分离 Web/代理实例、共享文件数据库下的真实凭据与控制权测试。

原生唯一中栏、同一 serve RID、持久化收据、会话锁、审批、只读 MCP 及 unknown 禁止重放均保留。没有开启旧 Council、变更生产自动调查/人工审批开关或执行生产修复。

## 本次验收方法

新增 `scripts/verify_native_vt.py` 与 `scripts/native_vt_client.cjs`：

- 执行未改写的实际 workbench.js、新建按钮和弹窗创建回调。
- 使用实际 WebApp 会话/终端/控制处理函数、真实 HTTP/WebSocket、真实 xterm 解析与屏幕缓冲区。
- 从全新会话开始，不先等后台 pane 预热，不用 tmux capture 内容代替前端画面断言。
- 在原生输入框发送中文任务与 Return；验证回答实际显示并对应完成收据。
- 通过页面断开/重连按钮进入同一 RID、serve 和 pane，不重发第一条消息；再次接管并发送第二条消息。
- 没有使用 HTTP prompt 捷径、模拟模型回答或修改只读边界。

这是 VT 集成验收，不是用户浏览器的视觉验收：DOM 和像素尺寸由无界面适配器提供；认证仅在私有回环测试适配器中替换为隔离主体，实际生产认证与权限逻辑另由回归覆盖。未操作用户正在使用的浏览器。临时 Node 依赖未进入生产应用依赖或 Git。
